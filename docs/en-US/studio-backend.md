# Studio backend protocol

[Português](../pt-BR/studio-backend.md) · **English** · [Deutsch](../de-DE/studio-backend.md)

`mxrb studio serve` runs MXRB as the backend of an IDE: a long-lived process
that speaks JSON-RPC 2.0 on stdin and stdout. Every IDE function that MXRB
owns (command catalog and tasks, Ruby project files, conversion, document
properties, typed model operations with undo and redo, Ruby/Mendix
synchronization, write coordination, ER and database queries) is one method
of `Mxrb::Studio::Service`. The IDE renders; MXRB decides and persists.

```sh
mxrb studio serve [--state-root DIR]
```

State (Ruby project links, synchronization bases, undo journals) lives under
`$XDG_STATE_HOME/mxrb/studio` unless `--state-root` is given.

## Framing and session

- One JSON-RPC message per line (NDJSON). JSON text never contains a raw
  newline, so a line is always a whole message.
- Requests run concurrently; replies can arrive in any order.
- The first request is `initialize`. The client states the protocol versions
  it speaks and, optionally, its workspace roots (used to attach file/line
  locations to errors):

```json
{"jsonrpc":"2.0","id":1,"method":"initialize",
 "params":{"protocol_versions":[2],"roots":["/work/shop-ruby"]}}
```

The reply names the protocol (`mxrb-studio` 2), the server version, every
method, the notifications and the capabilities (cancellation, progress, fork
isolation, undo, sync, locks). A client that speaks no supported version
receives error `-32015` with `data.supported`.

- `shutdown` waits for running requests and then refuses new ones; the `exit`
  notification ends the process. Closing stdin cancels what is still running.

## Methods

| Group | Methods |
|---|---|
| Catalog and tasks | `catalog/list`, `catalog/arguments`, `tasks/prepare`, `tasks/run`, `tasks/input`, `tasks/configurations`, `tasks/saveConfiguration`, `tasks/deleteConfiguration` |
| Files | `files/list`, `files/read`, `files/write`, `files/create`, `files/move`, `files/delete`, `files/worktrees`, `files/worktreeAdd`, `files/worktreeRemove` |
| Ruby | `ruby/syntax`, `ruby/declarations` |
| Project | `snapshot/create`, `project/status`, `project/convert`, `project/attach` |
| Documents | `documents/list`, `documents/read`, `documents/patch`, `documents/ruby` |
| Model | `model/capabilities`, `model/revision`, `model/preview`, `model/apply`, `model/history`, `model/undo`, `model/redo`, `model/catalog`, `model/domainDiagram` |
| Data | `data/logical`, `data/connections`, `data/physical`, `data/query`, `data/explain` |
| Parity | `parity/matrix` |
| Sync | `sync/link`, `sync/unlink`, `sync/status`, `sync/run`, `sync/preview` |
| Locks | `locks/acquire`, `locks/release`, `locks/status` |

`catalog/list` returns every public CLI command and scaffold with a typed
argument schema; `tasks/run` executes one as a child process and streams
`tasks/started` and `tasks/output` notifications. Cancelling the request
stops the task (`cancelled: true` in the result).

`ruby/syntax` parses with Prism and returns diagnostics with line and column;
`ruby/declarations` lists the Mendix artifacts a file declares (`entity`,
`page`, `microflow`, ...) with their qualified names. Neither evaluates Ruby.

`documents/ruby` takes `source_model`, `unit_id` (native unit UUID), and optional
`qualified_name`/BSON `type` identity checks. It returns `state: "ready"`, the
linked `root`, relative `path` and declaration `line`. Native identity, parsed
Prism declarations and flow identity metadata resolve the source without
executing Ruby or guessing filenames. The caller cannot supply a different root.
All exporter document families are supported, including module documents,
global settings/system texts/security/navigation, and project/module sources.
Generic `native_document` and `native_unit` declarations match the exact UUID,
so preserved extension types are not restricted to a named-document whitelist.
For aggregates with multiple source files, such as DomainModel, the response is
`state: "choose"`, `root`, and `files: [{path, line, label}]`. Domain entries
include the loader-verified index and entity/DTO/OQL view declarations; labels
use qualified entity names such as `Sudoku.Cell`. The host lets the user choose
before opening the editor. One file returns `ready`; conflicting duplicate
declarations remain `unavailable/ambiguous_source`.

A supported document without a linked Ruby project returns `missing_project`.
The host may ask the user to convert, save/snapshot the model, call
`project/convert`, then repeat the lookup and open its central editor. An absent,
unsupported, stale or ambiguous mapping returns `unavailable` with `reason` and
`message`. Existing Ruby workspaces are never regenerated by this read operation.
Infrastructure units preserved only in baseline JSON (Folder, ModuleGuidMapping,
ModuleSettings, ProjectConversion) do not fabricate a Ruby source file.

`files/write` and `documents/patch` take the revision the client last read
and fail with a conflict when the file or unit changed in between, so both
versions are kept.

## Panel operations

`tasks/configurations`, `tasks/saveConfiguration` and `tasks/deleteConfiguration`
keep named task configurations per `project` path in the state root. A saved
configuration stores a catalog command, its field values and extra arguments;
placeholders such as `{mpr}` stay unresolved. Unknown commands, fields or choices
are rejected when saving, and names are unique per project.

`files/delete` removes a file, or a folder with `recursive: true`; an optional
`revision` must still match. Git metadata and the workspace root cannot be
deleted. `files/worktreeAdd` adds a Git worktree at an absolute path outside the
current worktree, on a new or existing branch; `files/worktreeRemove` never forces
removal, so a worktree with local changes is kept. `project/attach` links the
native project to another worktree of the same Ruby project.

`data/connections` lists the database connections of a model with their
environment, host, port, database, user and running state. `data/physical`,
`data/query` and `data/explain` require an explicit `connection: {id}` and echo
the connection in every result; a missing or stale choice fails with
`connection_required` (-32020). Physical tables and foreign keys come only from
the PostgreSQL catalog; the logical model never confirms them. Query and explain
results include the executed SQL, so OQL translations are visible.

`parity/matrix` returns the parity matrix in both directions: Studio Pro
capabilities with their MXRB Ruby APIs/DSL from a reviewed inventory, and MXRB
operations with the IDE surface that reaches them, derived from the command
catalog and this protocol. Each capability has per-dimension states; nothing is
aggregated into a completion figure.

## Progress, cancellation and errors

- `$/cancelRequest` with `{"id": ...}` cancels a request.
- Long operations report `$/progress` notifications
  (`token` = request id, `kind` = `begin`/`report`/`end`, `current`, `total`,
  `detail`). Every MXRB operation that reports terminal progress reports here,
  and each report is a cancellation point.
- Evaluating a Ruby project and exporting a model run in a forked worker: a
  definition that exits, loops or exhausts memory cannot take the server down,
  and cancelling terminates the worker.

Errors are JSON-RPC error objects with `data.kind` and, when known,
`data.locations` (`file`, `line`, `column`):

| Code | `kind` | Meaning |
|---|---|---|
| -32700 / -32600 / -32601 / -32602 | `parse_error` / `invalid_request` / `method_not_found` / `invalid_params` | JSON-RPC conditions |
| -32002 | `not_initialized` | a request before `initialize` |
| -32800 | `cancelled` | the request was cancelled |
| -32010 | `conflict` | the target changed since it was read; nothing was overwritten |
| -32011 | `busy` | another writer holds the model; retry |
| -32012 | `validation` | the model or operation is invalid |
| -32013 | `toolchain` | a required tool or system call failed |
| -32014 | `ruby_source` | Ruby does not parse or evaluate; see `locations` |
| -32015 | `unsupported_protocol` | no common protocol version |
| -32603 | `internal_error` | anything else |

## Coordinated writes

Every MXRB writer of a model or workspace takes an exclusive `flock` on
`$XDG_STATE_HOME/mxrb/studio/locks/<sha256 of the canonical path>`. An IDE
that saves the same model takes the same lock, either directly or through
`locks/acquire` (the server holds the lock for the lease until
`locks/release` or the end of the connection). `locks/status` reports whether
someone holds it. MXRB waits up to 30 seconds and then answers `busy`.

## Undo and redo

`model/apply`, `documents/patch` and `sync/run` record a journal entry with the
exact native bytes of every unit they added, removed or changed. `model/undo`
restores them byte for byte (IDs, references and layout included);
`model/redo` reapplies them. An entry is only undone while its units still
hold the state it left; otherwise the request fails with a conflict and
nothing is written. The journal keeps the last 100 entries.

## Ruby and Mendix synchronization

`sync/preview` accepts `source_model` and optional
`expected_revisions: {"model": "<sha256>", "ruby": "<sha256>"}`. It resolves
the linked Ruby root, snapshots the saved native model, and compiles a private
copy of the Ruby tree. It never calls `sync/link`, updates original `.mxrb/`
metadata, replaces the Ruby binding, or writes the saved model. Temporary files
are removed on completion, errors and cancellation.

The response always includes `applied: false`,
`comparison: "saved_model_to_generated_ruby"`, and
`conflicts: {assessed: false, reason: "no_sync_baseline"}`. A completed preview
returns `state: "ready"`, `root`, `revisions`, `current_revisions`, `units` and
`validation: {errors, warnings}`. Each unit has its identity, type, name,
`action` (added/removed/modified), and element/property `changes` with before
and after values. Presence flags distinguish missing properties from null;
binary values use byte length and SHA-256. Changed inputs return `stale`;
an absent valid Ruby representation returns `missing_project`.
Relinking during generation also returns `stale`, with
`reason: "linked_project_changed"` and `current_root`; the new binding is preserved.

This compares saved inputs and the actual compilation result, not a three-way
merge or an apply plan. Compilation can normalize defaults without Ruby edits.
Name/position reconciliation does not guarantee preserved identity for future
application, and removed Ruby declarations can survive through native baseline
metadata. These limits are explicit in `limitations`.

Linux Bubblewrap isolation is mandatory: runtime, gems and MXRB libraries are
read-only; only a private worker directory is writable. The native comparison
snapshot stays outside that directory. The worker has separate process/network
namespaces, a temporary HOME and a reduced environment, without personal
credential folders. Failure to start isolation returns
`unavailable/isolation_unavailable` with no unrestricted fallback. Source
symlinks are rejected. Initial limits: 25,000 files/512 MiB of sources,
120 seconds of generation, 128 KiB of output. Ruby errors include file/line.

`sync/link` records the synchronized base of a model and its Ruby project: a
copy of the model, a copy of the Ruby files, the Ruby export of the model and
the model generated from the Ruby. `sync/status` is cheap: changed Ruby files
with their parse diagnostics and declared artifacts, changed Mendix units and
unresolved conflicts, summarized as `synced`, `pending`, `conversion_error` or
`conflict`.

`sync/run` synchronizes both directions:

1. **Mendix edits** are the units whose meaning differs from the base model.
   Property order, freshly generated IDs and the order of entities do not
   count as changes.
2. **Ruby edits** are the units whose generation from the current Ruby differs
   from the generation of the base Ruby. They are expressed as element
   operations (set a property, insert, remove or reorder a child) in the IDs
   of the model, so applying them keeps IDs, references, layout and every
   untouched property. Deleting the Ruby declaration of a document removes the
   document.
3. An element both sides changed is a **conflict**. A run with conflicts
   writes nothing and returns each conflict with the base, Mendix and Ruby
   values (`kind` `element`, `unit` or `file`). Running again with
   `resolutions` (`{"<conflict id>": "ruby" | "mendix"}`) applies everything.
4. Ruby edits are applied to the model in one journaled transaction, under the
   write lock, only if the model did not change during the run.
5. Mendix edits are merged into the Ruby files with a line-based three-way
   merge: comments and Ruby code outside the changed lines stay as they are. A
   change on one side next to an insertion on the other is not a conflict.
   Files that are overwritten are copied to the base's backup folder first.
6. `.mxrb/` (the native baseline and asset manifest) is owned by MXRB and
   always mirrors the synchronized model.

Ruby that does not parse or evaluate leaves the model untouched; the run fails
with `ruby_source` and the locations of the error. The last valid model stays
as it is and the Ruby changes stay pending.

`sync/status` also reports `diverged` units: units where the model generated
from the synchronized Ruby means something different from the model itself.
They show which parts of a model the Ruby projection does not capture yet;
their native content is preserved, not converted.

Measured on the public Sudoku sample (409 units, 355 Ruby files, Ruby 4.0,
one core per worker): linking 23 s, Ruby to Mendix 21 s (dominated by
generating the whole project from Ruby), Mendix to Ruby 5 s, `sync/status`
0.2 s.

## Single-shot use

`Mxrb::Studio::Backend#call` accepts one request object with a version 1
`action` name (`catalog`, `file_read`, `model_apply`, ...) and reaches the same
methods, for clients that start one process per request.

## Studio Pro panels

The additional `frontend/modeler/studio.html` entry provides the Ruby App Explorer,
MXRB Tasks, Global ER, Database and Parity panels in React. Build it with `npm run build:studio` from
`frontend/modeler`; the compiled entry and local assets ship in the gem. Node is
only a build dependency. This separate build preserves the existing modeler bundles.

Panels speak the protocol above through `chrome.webview.postMessage` and its
`message` event. The desktop host owns the Ruby process, negotiates protocol 2 and
maps page request IDs to its shared connection. It additionally handles
`host/context` and `host/contextChanged`: project `root`, `source_model`, optional
`ruby_root` and `theme` CSS variables named `--studio-*`. These two messages belong
to the desktop adapter, not `Mxrb::Studio::Service`. Panels cannot shut down the
shared process. When the context advertises `capabilities.native_dialogs`, panels
ask the host for Rename/Warning dialogs with `host/dialog`
(`{kind: "prompt"|"confirm", title, message, label, value, buttons}` →
`{button, value}`); otherwise they show an equivalent in-page dialog.

Before each task, the panel resolves `project/status` if the host did not supply
`ruby_root`. A conversion or link made in another dock therefore supplies the
working directory and `{ruby}` substitution immediately. `{root}` follows that
working directory; `{mpr}` continues to identify the native model. Without a
linked representation, native/global commands can use the source directory, but
Ruby-context commands ask for conversion or linking first. Project changes and
Stop cancel pending resolution as well as task execution.

Run `npm run test:studio` in `frontend/modeler` for the workspace/cancellation
regressions. `studio_tasks_linked_flow.json` adds a Tasks-only browser scenario:
its host supplies `panel: "tasks"`, `root` and `source_model` (no `ruby_root`) for
a synthetic model whose linked Ruby project contains module `Shop`. It runs the
real `project inspect` command and checks the converted project output.

The Explorer supports project link lookup/conversion, lazy folder reads,
virtualized rows, add file/folder, rename and delete through Studio Pro dialogs
supplied by the host (`host/dialog`), and Git worktrees. Tasks group the real
catalog like IntelliJ's Maven window, keep saved tasks per project and show output
with Stop, Clear and Scroll lock. The Global ER shows the logical model of all
modules on one canvas; the Database panel shows physical schema, SQL/OQL results
and plans only for an explicitly chosen connection; the Parity panel shows
`parity/matrix`. Browser scenarios under
`spec/fixtures/frontend_browser/studio_*_flow.json` exercise the panels with
synthetic files, a public sample app and, for `studio_database_live_flow.json`,
a running MXRB database workspace; they do not establish full IDE parity.

The host can publish a numeric `project_revision` in `host/contextChanged` when a
conversion or link change keeps the same `source_model`. The Explorer then queries
`project/status` again and drops the previous selection and listing, and Tasks
cancels the pending operation. The native host uses this revision to invalidate
the context instead of caching `ruby_root` as a permanent link.
`studio_project_revision_flow.json` checks that transition and the cancellation of
late responses against the synthetic host served by
`node frontend/modeler/test/studio/contextRevisionServer.mjs 4587`. The same server
answers `/studio.html?fixture=sync` for the `studio_sync_preview*_flow.json`
scenarios. The synthetic hosts are TypeScript sources in
`spec/fixtures/frontend_browser`, served with their types stripped.
